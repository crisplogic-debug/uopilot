0. ДОПУЩЕНИЯ И ОТКРЫТЫЕ ВОПРОСЫ
================================================================================

Допущения (приняты для данного ТЗ; при расхождении с требованиями заказчика
документ подлежит корректировке):

  A1. Целевая ОС: Windows 10/11 (основная); захват экрана через DXGI Desktop
      Duplication API или Win32 BitBlt как fallback.
  A2. Язык реализации: Python 3.11+ (ядро ML и пайплайн данных); критичные
      по задержке участки инференса — ONNX Runtime (CPU/GPU).
  A3. Режим работы: локально, без облачной отправки данных.
  A4. Выход модели для задачи «столбик заброса»: непрерывная оценка
      заполненности fill_ratio ∈ [0.0, 1.0] + бинарный флаг in_perfect_zone.
  A5. Система может как автоматически отпускать ЛКМ, так и только сигнализировать
      пользователю (режим выбирается в настройках).
  A6. Область захвата (ROI) задаётся пользователем вручную один раз на сессию
      или сохраняется как пресет.
  A7. Latency budget ML-инференса: строго < 10 мс от получения кадра ROI до
      готового результата предсказания (до момента принятия решения об отпуске
      ЛКМ). Захват экрана и эмуляция ввода не входят в этот бюджет.
  A8. Интерфейс: полноценное GUI-приложение (не CLI). Все режимы (сбор данных,
      разметка, обучение, инференс, настройки) доступны из единого окна.
  A9. Поддержка масштабирования Windows DPI (125%, 150%, 200% и др.):
      корректный захват, координаты ROI и пресеты с учётом dpi_scale.
  A10. Ускорение: GPU обязателен как целевая платформа инференса (CUDA /
       DirectML через ONNX Runtime) для обработки больших областей захвата
       (до 1920×1280 px). CPU — fallback при недоступности GPU.
  A11. Референсное целевое железо заказчика:
       • GPU: NVIDIA GeForce RTX 4080 (16 GB VRAM)
       • CPU: Intel Core i5-14700
       • RAM: 64 GB DDR5
       Все бенчмарки latency и рекомендации пайплайна (раздел 14) ориентированы
       на эту конфигурацию.

Уточнённые требования заказчика (зафиксированы):

  R1. Задержка ML-поиска в области и получения результата: < 10 мс (p95).
  R2. Полноценный GUI со всеми функциями пайплайна.
  R3. Поддержка DPI-масштабирования; поэтапное развитие задач распознавания:
      • Фаза 1 — столбик прогресса заброса (узкий ROI, регрессия fill_ratio).
      • Фаза 2 — круглые объекты ~200×200 px на большой области игрового окна.
  R4. GPU (CUDA / DirectML) для ускорения; целевой размер области захвата
      до 1920×1280 px при сохранении latency ML-инференса < 10 мс.

Визуальная модель столбика (зафиксировано, Q4 закрыт):

  V1. Тело столбика (заполненная часть): белый / светло-серый оттенок,
      полупрозрачный.
  V2. Незаполненная часть столбика: прозрачная — виден меняющийся фон
      (светлый, тёмный, вода и т.д.).
  V3. Perfect zone: верхняя зона столбика, визуально выделена градиентной
      заливкой в зелёный цвет (не абстрактный порог fill_ratio, а отдельный
      цветовой сегмент на экране).
  V4. Следствие для ML: модель должна одновременно локализовать столбик,
      оценивать % заливки и детектировать зелёную perfect zone как
      семантический сегмент (или bbox/маску зоны).

================================================================================
1. ОБЩЕЕ ОПИСАНИЕ ФУНКЦИОНАЛА
================================================================================

1.1. Назначение
---------------
ML-модуль uopilot предназначен для:
  • захвата заданной прямоугольной области экрана (Region of Interest, ROI);
  • обнаружения целевого объекта (первичный кейс: полупрозрачный столбик
    прогресса заброса удочки);
  • оценки степени заполненности столбика (высота заполненной части относительно
    общей высоты столбика);
  • определения момента попадания заполненности в «perfect zone»;
  • генерации события «отпустить ЛКМ» или визуального/звукового сигнала.

1.2. Характеристики целевого объекта (кейс «столбик заброса»)
---------------------------------------------------------------
  Параметр              | Диапазон / поведение
  ----------------------|--------------------------------------------------
  Ширина столбика       | 8–50 px, может плавно меняться в процессе сессии
  Высота столбика       | 220–1000 px, может плавно меняться
  Заполнение            | Белый/светлый полупрозрачный сегмент снизу вверх
  Пустая часть          | Прозрачная — сквозь неё виден переменный фон
  Perfect zone          | Верхняя зона столбика, градиент в зелёный цвет
  Фон                   | Светлый, тёмный, вода и др.; меняется динамически
  Движение заполнения   | Циклическое: рост 0 → max → perfect zone → снижение
  Скорость цикла        | Постоянна в рамках одной игровой сессии, различна
                        | между сессиями

1.2.1. Дорожная карта задач распознавания
-----------------------------------------
  ФАЗА 1 (MVP) — столбик заброса удочки
    • ROI: узкая область вокруг столбика (типично 50–200 × 220–1000 px).
    • Задача: регрессия fill_ratio + детекция perfect zone.
    • Latency ML-инференса: < 10 мс (p95), в т.ч. на GPU.

  ФАЗА 2 — круглые объекты на игровом поле
    • ROI: большая область игрового окна (до 1920×1280 px).
    • Объект: круглые элементы ~200×200 px (детекция bbox / центра + радиус).
    • Требует GPU-инференса и оптимизированного детектора (YOLO-Nano / SSD);
      полный кадр 1920×1280 на CPU не укладывается в бюджет < 10 мс.
    • Стратегии ускорения: GPU FP16, TensorRT / DirectML, тайловый инференс
      (скользящее окно 256×256 с шагом), ROI-трекинг после первичной детекции.

1.3. Режимы работы приложения
-----------------------------
  РЕЖИМ «ИГРА + СБОР ДАННЫХ»
    Пользователь играет вручную; система в фоне сохраняет кадры ROI,
    метаданные и опционально события ввода (нажатие/отпускание ЛКМ).

  РЕЖИМ «РАЗМЕТКА»
    Инструменты аннотирования накопленных кадров после сессии сбора.

  РЕЖИМ «ОБУЧЕНИЕ»
    Подготовка датасета, обучение / дообучение модели, валидация метрик.

  РЕЖИМ «ИНФЕРЕНС» (боевой)
    Захват ROI → предсказание модели → действие или сигнал пользователю.

  РЕЖИМ «УНИВЕРСАЛЬНЫЙ ПОИСК»
    Применение обученной или предобученной модели к другим классам объектов
    (см. раздел 7).

1.4. Пользовательский сценарий (happy path)
-------------------------------------------
  1. Пользователь задаёт ROI на экране (перетаскиванием рамки).
  2. Выбирает режим «Игра + сбор данных»; играет несколько сессий.
  3. Переходит в «Разметку»; корректирует автоматические и ручные метки.
  4. Запускает «Обучение»; получает модель с приемлемыми метриками.
  5. Подключает модель в режиме «Инференс»; система отпускает ЛКМ в perfect zone.
  6. При изменении визуала игры — дообучает модель на новых кадрах.

1.5. Ограничения
----------------
  • ML-модуль не изменяет память процесса игры; только захват экрана и эмуляция
    ввода (SendInput / библиотека низкоуровневого ввода).
  • Точность зависит от объёма и качества разметки.
  • При смене разрешения или DPI-масштаба Windows система пересчитывает ROI;
    при существенном изменении визуала — дообучение модели.
  • Область захвата до 1920×1280 px поддерживается только с GPU-инференсом
    и оптимизированным пайплайном (см. разделы 8 и 10).

================================================================================
2. СОВМЕЩЕНИЕ ИГРЫ ПОЛЬЗОВАТЕЛЕМ И НАКОПЛЕНИЕ ИСХОДНЫХ МАТЕРИАЛОВ
================================================================================

2.1. Цель
---------
Обеспечить пассивный и активный сбор обучающих данных без прерывания игрового
процесса, с минимальным влиянием на производительность ПК.

2.2. Функциональные требования
------------------------------

  F2.1. Захват ROI
    • Частота захвата: настраиваемая, по умолчанию 30 FPS (макс. 60 FPS).
    • Формат кадра: PNG (без потерь, для архива) или RAW ndarray; для
      онлайн-пайплайна — внутренний буфер BGR/RGBA.
    • Сохранять timestamp (мс), номер кадра, хеш сессии.

  F2.2. Запись сессии
    • Одна игровая сессия = каталог:
        data/raw/<session_id>/
          frames/          — изображения ROI
          meta.jsonl       — метаданные построчно (JSON Lines)
          events.jsonl     — события ввода (опционально)
          config.json      — ROI, разрешение экрана, DPI, версия клиента
    • session_id: UUID v4, время начала UTC.

  F2.3. События ввода (опционально, рекомендуется)
    • Глобальный хук или polling состояния ЛКМ:
        { "t": <timestamp_ms>, "type": "mouse", "button": "left",
          "action": "down"|"up", "synthetic": false }
    • Используется как слабая разметка (weak labels) и для синхронизации
      момента «правильного» отпускания.

  F2.4. Умный сэмплинг (снижение объёма данных)
    • Не сохранять идентичные кадры (perceptual hash / порог MSE).
    • Повышенная частота сохранения в окрестности perfect zone (±N кадров
      от предполагаемой зоны по эвристике или прошлой модели).
    • Равномерное покрытие диапазона fill_ratio (стратификация).

  F2.5. Режимы сбора
    • CONTINUOUS — запись всех отфильтрованных кадров.
    • TRIGGER — запись только при обнаружении столбика (предварительный
      детектор: контур + вертикальная структура или лёгкая модель).
    • MANUAL_MARK — пользователь клавишей помечает «сейчас perfect»;
      сохраняется кадр ± буфер соседних кадров.

  F2.6. GUI и оверлей во время игры
    • Полноценное главное окно + компактный оверлей поверх игры:
      индикатор записи, счётчик кадров, текущий fill_ratio (если модель активна),
      latency ML (мс), горячие клавиши (старт/стоп, ручная метка, пауза, panic).
    • Оверлей не перекрывает ROI; поддержка DPI-масштабирования.
    • Панель «Захват»: выбор монитора, рисование ROI мышью, пресеты, dpi_scale.

  F2.7. Производительность
    • Запись на диск — асинхронная очередь (отдельный поток/процесс).
    • Целевая нагрузка: ≤ 5% CPU при 30 FPS и узком ROI (фаза 1).
    • Для большого ROI (до 1920×1280, фаза 2): основная нагрузка на GPU;
      захват экрана — отдельный поток, ML-инференс < 10 мс на кадр (p95).

2.3. Метаданные кадра (meta.jsonl, одна строка = один кадр)
-----------------------------------------------------------
  {
    "frame_id": "uuid",
    "session_id": "uuid",
    "timestamp_ms": 1717654321000,
    "frame_index": 1024,
    "roi": { "x": 100, "y": 200, "w": 80, "h": 900 },
    "screen": { "width": 1920, "height": 1080, "dpi_scale": 1.0 },
    "weak_label": {
      "fill_ratio": null,
      "in_perfect_zone": null,
      "source": "none|heuristic|model_v3"
    },
    "saved_reason": "continuous|trigger|manual|near_perfect"
  }

2.4. Критерии достаточности датасета (рекомендации)
---------------------------------------------------
  • Минимум для первого обучения: 2 000 размеченных кадров.
  • Рекомендуемый объём: 10 000+ кадров с балансом по fill_ratio и типу фона.
  • Не менее 3 игровых сессий с разным освещением / локацией фона.

================================================================================
3. РАЗМЕТКА ДАННЫХ ОБУЧЕНИЯ (ПОСЛЕ НАКОПЛЕНИЯ)
================================================================================

3.0. Нужна ли разметка вообще?
-------------------------------
  Да, но объём зависит от стадии и может быть минимизирован.

  Без ручной разметки (только сбор):
    • Накопление сырых кадров и weak labels (момент отпускания ЛКМ).
    • Недостаточно для первого обучения с требуемой точностью (MAE ≤ 0.03).

  Минимально необходимая разметка для первого обучения:
    • ≥ 500 кадров с verified-метками: bar_bbox + fill_ratio + perfect zone.
    • Можно начать с 2000 авто-предразметенных + 500 ручных правок (active learning).

  Когда разметка не нужна в полном объёме:
    • После обучения базовой модели — дообучение на кадрах с предразметкой
      моделью и ручной правкой только low-confidence (10–20% выборки).
    • Для инференса в бою — разметка не используется.

  Рекомендуемая стратегия:
    1) Сбор сырья (игра + авто-сохранение ROI).
    2) Первичная ручная разметка репрезентативной выборки (~500–2000 кадров).
    3) Обучение универсальной модели (раздел 4.1.1).
    4) Далее — active learning: модель предразмечает, пользователь правит
       только ошибки; новые размеченные кадры идут в пул дообучения.

3.1. Цель
---------
Преобразовать сырые кадры в размеченный датасет с целевыми значениями для
обучения регрессии заполненности и (опционально) детекции perfect zone.

3.2. Типы разметки
------------------

  Тип R1 — Регрессия заполненности (обязательный)
    • fill_ratio: float [0.0, 1.0] — отношение высоты заполненной части
      столбика к полной высоте столбика на кадре.
    • Альтернатива: fill_height_px + bar_height_px (модель вычисляет ratio).

  Тип R2 — Perfect zone (обязательный для автоклика)
    • in_perfect_zone: bool — уровень заливки пересекает зелёную зону.
    • perfect_zone_mask или perfect_zone_bbox — сегмент верхней зоны с
      зелёным градиентом (приоритетная разметка; не только норм. координаты).
    • perfect_zone_bounds: { "y_top_norm", "y_bottom_norm" } — fallback,
      нормализованные координаты внутри bar_bbox.

  Тип R3 — Детекция столбика (рекомендуется)
    • bar_bbox: [x, y, w, h] в координатах ROI.
    • bar_visible: bool — столбик присутствует на кадре.

  Тип R4 — Вспомогательная классификация фона (опционально)
    • background_class: enum [light, dark, water, other]
    • Помогает стратифицировать выборку и аугментации.

  Тип R5 — Круглые объекты, фаза 2 (после столбика)
    • object_bbox: [x, y, w, h] (~200×200 px)
    • object_center: [cx, cy]
    • object_radius: float (px)
    • object_class: string (если несколько типов кругов)
    • Инструмент разметки: bbox + авто-подгонка круга (Shift — идеальный круг)

3.3. Инструменты разметки
-------------------------

  UI-аннотатор (встроенный):
    • Просмотр кадров с таймлайном по session_id.
    • Ползунок fill_ratio с привязкой к визуальной линии на превью.
    • Выделение bbox столбика мышью; авто-подстройка ширины под 8–50 px.
    • Горячие клавиши: ←/→ кадр, P — perfect zone, S — пропустить, D — дубликат.
    • Полуавтоматическая разметка: предзаполнение от последней обученной модели
      (active learning); пользователь правит только ошибки.

  Импорт / экспорт:
    • COCO JSON (детекция), CSV (регрессия), custom JSONL (native формат uopilot).
    • Экспорт в YOLO format (если выбран детектор YOLO).

3.4. Автоматическая предразметка
--------------------------------
  • При наличии модели vN: прогон по неразмеченным кадрам → сохранение
    confidence; в приоритет очереди разметчика — кадры с низким confidence
    или расхождением с weak labels от ЛКМ.
  • Эвристический предиктор (baseline до первой модели):
    анализ вертикального градиента яркости / цвета в центре ROI.

3.5. Контроль качества разметки
-------------------------------
  • Статистика распределения fill_ratio (гистограмма).
  • Поиск выбросов: скачок fill_ratio > порога между соседними кадрами
    при стабильной скорости (флаг для ручной проверки).
  • Inter-annotator agreement (если два человека размечают подвыборку).
  • Статус кадра: unlabeled | auto_labeled | verified | rejected.

3.6. Структура размеченного датасета
------------------------------------
  data/labeled/<dataset_version>/
    images/                    — симлинки или копии кадров
    annotations.jsonl          — полная разметка
    splits/
      train.txt
      val.txt
      test.txt
    dataset_manifest.json      — версия, дата, статистика, checksum

4. ОБУЧЕНИЕ НОВОЙ МОДЕЛИ, СОХРАНЕНИЕ И ПОДКЛЮЧЕНИЕ
================================================================================

4.1. Универсальная архитектура модели (multi-task)
--------------------------------------------------
  Цель: одна базовая модель с общим backbone и сменяемыми головами,
  покрывающая фазу 1 (столбик) и расширяемая на фазу 2 (круги) и другие
  объекты через дообучение без смены всего пайплайна.

  Архитектура «UopilotNet» (рекомендуемая):

    Вход: тензор кадра ROI (BGR/RGB, нормализованный)
         ↓
    [Shared Backbone]  — EfficientNet-Lite0 или YOLOv8n backbone (pretrained)
         ↓
    ┌────────────┬──────────────┬─────────────────┐
    │ Head-Det   │ Head-Seg     │ Head-Reg        │
    │ bar_bbox   │ bar_mask     │ fill_ratio      │
    │ (+ классы) │ perfect_zone │ (scalar)        │
    │            │ _mask (зел.) │                 │
    └────────────┴──────────────┴─────────────────┘

  Выходы для задачи fishing_bar:
    • bar_bbox, bar_visible          — поиск столбика на кадре
    • fill_ratio                       — % заливки белым сегментом
    • perfect_zone_mask / in_perfect_zone — зелёная верхняя зона
    • confidence per head

  Расширение на новые объекты (фаза 2+):
    • Добавление классов в Head-Det (круглые объекты, HP-бары и т.д.)
      или новой головы через freeze backbone + train new head.
    • Fine-tune на размеченных кадрах нового типа; старые головы — опционально
      заморожены (freeze) или совместное обучение с малым lr.

  Преимущества:
    • Единый inference-пайплайн (раздел 14).
    • Один экспорт ONNX с несколькими выходами.
    • Дообучение = новые данные + новые классы/головы, без переписывания GUI.

4.1.2. Поддерживаемые архитектуры (см. также раздел 8)
------------------------------------------------------
  Уровень 1 — Baseline (без нейросети, для sanity check)
    • Классический CV: поиск вертикальных рёбер, цветовая сегментация в HSV.

  Уровень 2 — Лёгкая CNN-регрессия (рекомендуется для MVP)
    • Вход: кроп ROI, ресайз до фиксированного размера (например 64×256).
    • Выход: fill_ratio (sigmoid), in_perfect_zone (sigmoid), bar_bbox (опц.).
    • Backbone: MobileNetV3-Small / EfficientNet-Lite0.

  Уровень 3 — Детектор + регрессия в ROI
    • YOLO-Nano / YOLOv8n для bar_bbox; отдельная голова регрессии на кропе.

  Уровень 4 — Temporal (опционально, фаза 2)
    • 1D-CNN / tiny LSTM по последовательности из N кадров для сглаживания
      и предсказания момента пересечения perfect zone.

4.2. Процесс обучения
--------------------
  1. Загрузка dataset_manifest.json, проверка целостности.
  2. Аугментации (см. раздел 6).
  3. Обучение с ранней остановкой по val_loss.
  4. Расчёт метрик на test (см. 4.4).
  5. Экспорт в ONNX + сохранение артефактов.

4.3. Сохранение модели
----------------------
  models/<model_name>/<version>/
    model.onnx                 — основной артефакт для инференса
    model.pth                  — веса PyTorch (для дообучения)
    config.yaml                — гиперпараметры, размер входа, нормализация
    metrics.json               — MAE, RMSE, F1 perfect zone, latency benchmark
    labels.json                — список выходных тензоров и их смысл
    README.txt                 — краткое описание и условия применимости

  Реестр моделей (models/registry.json):
    • id, name, version, task_type, created_at, metrics_summary, path, active: bool

4.4. Метрики качества
---------------------
  Регрессия fill_ratio:
    • MAE ≤ 0.03 (нормализованная высота)
    • RMSE ≤ 0.05

  Классификация perfect zone:
    • Precision ≥ 0.95, Recall ≥ 0.95 на тестовой выборке
    • False release rate (преждевременный клик) ≤ 1%

  Производительность:
    • Inference latency p95 < 10 мс (обязательное требование R1) для целевого
      ROI задачи: фаза 1 — узкий ROI на GPU; фаза 2 — 1920×1280 на GPU.

4.5. Подключение сохранённой модели
-----------------------------------
  • GUI: выбор из реестра models/registry.json (вкладка «Модели»).
  • Параметры подключения:
      - model_path (ONNX)
      - input_size [W, H]
      - confidence_thresholds { fill, perfect }
      - temporal_smoothing: { enabled, window_frames: 3 }
      - action_policy: { mode: "auto_release"|"signal_only", cooldown_ms: 100 }
  • Hot-reload: смена модели без перезапуска захвата ROI (атомарная подмена
    сессии ONNX Runtime).
  • Валидация при подключении: пробный инференс на тестовом тензоре;
    несовпадение размеров входа → ошибка с понятным сообщением.

4.6. Логирование инференса
--------------------------
  • Опциональный лог predictions.jsonl для отладки:
    timestamp, fill_ratio, in_perfect_zone, latency_ms, model_version.

================================================================================
5. ДООБУЧЕНИЕ (FINE-TUNING) МОДЕЛИ
================================================================================

5.1. Сценарии дообучения
------------------------
  S1. Новый визуальный патч игры (фон, цвет столбика).
  S2. Изменение диапазона размеров столбика (новый контент).
  S3. Добавление размеченных кадров из редких условий (ночь, дождь, вода).
  S4. Снижение false positive после анализа логов инференса.

5.2. Функциональные требования
------------------------------
  F5.1. Загрузка базовой модели (model.pth + config.yaml).
  F5.2. Заморозка backbone (опция): обучение только голов регрессии.
  F5.3. Меньший learning rate (например 1e-4 → 1e-5) и меньше эпох.
  F5.4. Объединение старого train set + новых данных (rehearsal); опция
        replay_buffer с выборкой 20% старых кадров против catastrophic forgetting.
  F5.5. Версионирование: новая версия v1.1, старая v1.0 остаётся в реестре.
  F5.6. A/B сравнение: одновременный прогон v1.0 и v1.1 на val — отчёт
        «стало лучше / хуже» по метрикам.
  F5.7. Откат (rollback) к предыдущей версии одним действием в UI.

5.3. Минимальный объём для дообучения
---------------------------------------
  • Не менее 200 новых verified кадров, желательно 500+.

5.4. Active learning loop
-------------------------
  1. Инференс в боевом режиме с флагом «сохранять low confidence».
  2. Пользователь размечает только отобранные кадры.
  3. Fine-tune → валидация → публикация новой версии.

================================================================================
6. ОБРАБОТКА ДАННЫХ ДЛЯ ОБУЧЕНИЯ (РАЗМЕТКА, КЛАССИФИКАЦИЯ)
================================================================================

6.1. Пайплайн подготовки данных
-------------------------------
  [raw sessions] → dedup → filter (blur/low quality) → [optional auto-label]
       → manual label → QA → split → augment → [tfrecord/onnx-ready tensors]

6.2. Очистка и фильтрация
-------------------------
  • Удаление размытых кадров (variance Laplacian < порога).
  • Удаление кадров без столбика (bar_visible = false), если задача только
    регрессия заполненности при наличии столбика.
  • Балансировка классов фона (background_class).

6.3. Аугментации (offline, при обучении)
----------------------------------------
  • Яркость / контраст ±20%
  • Гамма-коррекция
  • Гауссов шум
  • Случайный сдвиг ROI ±2 px
  • Имитация прозрачности столбика (alpha blending с случайным фоном)
  • Горизонтальное отражение — только если симметрично допустимо в игре
  • Масштабирование столбика в пределах 8–50 × 220–1000 px (random resize crop)

6.4. Нормализация
-----------------
  • ImageNet mean/std или per-dataset статистика (сохраняется в config.yaml).
  • fill_ratio всегда в [0, 1]; bar_bbox нормализовать к [0, 1] относительно ROI.

6.5. Классификация вспомогательных задач
----------------------------------------
  При необходимости обучаются отдельные головы или модели:
    • bar_present: есть / нет столбика на кадре
    • background_type: light / dark / water / other
    • game_state: мини-игра активна / не активна

  Использование: gating — регрессия заполненности запускается только если
  bar_present = true и game_state = active.

6.6. Сплиты train / val / test
------------------------------
  • По умолчанию 70 / 15 / 15, стратификация по session_id (кадры одной сессии
    не попадают в разные сплиты — предотвращение утечки).
  • Фиксированный seed для воспроизводимости.

================================================================================
7. УНИВЕРСАЛЬНОЕ ИСПОЛЬЗОВАНИЕ МОДЕЛИ ДЛЯ ПОИСКА ДРУГИХ ОБЪЕКТОВ
================================================================================

7.1. Концепция
--------------
ML-подсистема проектируется как набор «задач» (Task), каждая задача определяет:
  • тип объекта и классы;
  • формат выхода (bbox, mask, keypoints, scalar regression);
  • ROI или полноэкранный поиск;
  • политику действий (клик, сигнал, none).

Задача «fishing_bar» — эталонная (reference implementation).
  Все задачи используют общий backbone UopilotNet (раздел 4.1.1); различие —
  в наборе активных голов и классов детектора.

7.2. Реестр задач (tasks/)
--------------------------
  tasks/<task_id>/
    task.yaml              — описание задачи
    class_names.json
    default_model          — симлинк на models/...
    roi_preset.json        — опционально

  Пример task.yaml:
    id: fishing_bar
    type: multi_task (UopilotNet)
    outputs: [bar_bbox, bar_visible, fill_ratio, perfect_zone_mask,
              in_perfect_zone, confidence]
    input_size: [64, 256]
    model_artifact: model.trt  # TensorRT FP16, приоритет на RTX 4080

  Пример task.yaml для фазы 2 (круглые объекты):
    id: round_objects_200
    type: detection
    outputs: [object_bbox, object_center, object_radius, confidence]
    object_shape: circle
    typical_size_px: [200, 200]
    capture_roi_max: [1920, 1280]
    perf_profile: latency_gpu
    inference_provider: CUDAExecutionProvider | DmlExecutionProvider

  Пример task.yaml для другого объекта:
    id: enemy_hp_bar
    type: detection + regression
    outputs: [hp_bar_bbox, hp_ratio]

7.3. Режимы поиска объектов
---------------------------
  • ROI-scoped — пользователь задал область; модель ищет только внутри ROI
    (быстрее, подходит для столбиков UI).
  • Large-window GPU detection — для области до 1920×1280 px (фаза 2);
    YOLO-Nano / YOLOv8n на GPU (FP16), latency < 10 мс; обязательный режим
    для круглых объектов 200×200 px.
  • Full-screen sliding / tiled — fallback: тайлы 256×256 с перекрытием 25%;
    агрегация NMS по детекциям; применяется если single-pass не укладывается
    в бюджет на конкретном GPU.
  • Template-assisted — комбинация классического template matching для
    грубого положения + ML для точной оценки состояния.

7.4. Требования к добавлению новой задачи
-----------------------------------------
  1. Описать task.yaml.
  2. Собрать и разметить датасет (разделы 2–3).
  3. Обучить или дообучить модель (раздел 4–5).
  4. Зарегистрировать в tasks/ и models/registry.json.
  5. Настроить action_policy (клик / клавиша / none).

7.5. Общий интерфейс инференса (API)
------------------------------------
  class InferenceEngine:
      load_model(model_path, config)
      predict(frame_bgr, task_id) -> PredictionResult
      predict_sequence(frames[], task_id) -> List[PredictionResult]  # опц.

  PredictionResult:
      boxes: List[BBox]
      scalars: Dict[str, float]      # fill_ratio, hp_ratio, ...
      flags: Dict[str, bool]           # in_perfect_zone, ...
      confidence: float
      latency_ms: float

7.6. Перенос весов между задачами
---------------------------------
  • Transfer learning: общий backbone (ImageNet pretrained), разные головы.
  • При дообучении на новой задаче — новый task_id и отдельная версия модели;
    backbone может быть общим файлом (shared weights).

================================================================================
8. ВЫБОР ОПТИМАЛЬНОЙ ML-МОДЕЛИ И ПАРАМЕТРОВ
================================================================================

8.1. Критерии выбора
--------------------
  Приоритет зависит от профиля задачи (настраивается в task.yaml → perf_profile):

  PROFILE "latency_gpu" (основной для продакшена, R1 + R4)
    • Фаза 1: MobileNetV3-Small, вход 64×256, ONNX Runtime GPU (CUDA/DirectML)
    • Фаза 2: YOLOv8n / YOLO-Nano, вход 640×640 или letterbox 1280×832,
      FP16, TensorRT или DirectML EP
    • Graph optimization: all; IO binding на GPU
    • Целевой latency p95 < 10 мс

  PROFILE "latency_cpu" (fallback при отсутствии GPU)
    • MobileNetV3-Small + линейная голова; только узкий ROI (фаза 1)
    • Вход 48×192; INT8 квантизация
    • Большой ROI 1920×1280 на CPU не поддерживается в рамках R1

  PROFILE "accuracy" (максимальная точность, offline / не realtime)
    • EfficientNet-B0 или YOLOv8s + regression head
    • Вход 128×512 (фаза 1) / 1280×1280 (фаза 2)
    • Temporal smoothing 5 кадров; FP32

  PROFILE "balanced" (рекомендуется по умолчанию для фазы 1)
    • MobileNetV3 или EfficientNet-Lite0
    • Вход 64×256
    • FP16 на GPU; temporal smoothing 3 кадра
    • latency p95 < 10 мс на GPU

8.2. Сравнительная таблица кандидатов
-------------------------------------
  Модель                  | Парам. | Latency CPU* | MAE fill** | Примечание
  ------------------------|--------|--------------|------------|------------------
  CV baseline             | —      | < 1 ms       | ~0.08      | Хрупко на воде
  MobileNetV3-Small       | ~2M    | 3–8 ms       | ~0.03      | Лучший MVP
  EfficientNet-Lite0      | ~4M    | 5–12 ms      | ~0.025     | Чуть точнее
  YOLOv8n + crop head     | ~3M    | 8–15 ms      | ~0.02      | Если bbox плавает
  YOLOv8n full frame      | ~3M    | 25–40 ms     | ~0.02      | Без фикс. ROI

  * Фаза 1: ROI 64×256; Фаза 2: 1920×1280 → letterbox 640×640
    GPU: NVIDIA GTX 1660+ / AMD с DirectML; batch=1, ONNX Runtime
  ** Ожидаемое при 10k размеченных кадров

  Доп. строка для фазы 2 (круглые объекты 200×200):
  YOLOv8n + GPU FP16   | ~3M    | 4–9 ms       | mAP@0.5 ≥0.90 | 1920×1280 ROI

8.3. Автоподбор гиперпараметров (AutoML-lite)
---------------------------------------------
  Скрипт benchmark_models.py:
    • Перебор {backbone × input_size × quantization} на val-наборе.
    • Ограничения: latency_p95 < 10 мс (R1), MAE < target, GPU provider обязателен
      для ROI ≥ 1280×720.
    • Выход: отчёт models/benchmarks/<date>.json + рекомендация.

  Настраиваемые параметры:
    - input_width, input_height
    - learning_rate, batch_size, epochs
    - temporal_window
    - confidence_threshold_perfect
    - smoothing: exponential | median

8.4. Параметры для задачи «столбик заброса» (рекомендация MVP)
--------------------------------------------------------------
  backbone:         MobileNetV3-Small (pretrained ImageNet)
  input_size:       64 × 256 (W × H)
  outputs:          fill_ratio (MSE), in_perfect_zone (BCE)
  optimizer:        AdamW, lr=1e-3, weight_decay=1e-4
  batch_size:       32
  epochs:           50 (early stopping patience=8)
  loss_weights:     { fill: 1.0, perfect: 2.0 }
  temporal_smoothing: EMA alpha=0.4 по fill_ratio
  perfect_trigger:  in_perfect_zone == true AND d(fill)/dt ≈ 0 (плато) OR
                    пересечение порога сверху вниз при нисходящей фазе —
                    пересечение белой заливки с зелёной perfect zone
                    (детекция сегмента Head-Seg, см. V3)

8.5. Квантизация и деплой
-------------------------
  • Post-training INT8 (ONNX Runtime) после калибровки на 200–500 кадрах.
  • Ожидаемое ускорение CPU: 1.5–2.5× при деградации MAE не более +0.005.
  • При недопустимой деградации — оставить FP32.

8.6. Бенчмаркинг на целевом железе
----------------------------------
  Обязательный отчёт перед релизом модели:
    - latency: mean, p95, p99 (1000 прогонов)
    - CPU / RAM usage во время инференса
    - сравнение с предыдущей версией модели

10. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
================================================================================

  Производительность:
    • ML-инференс p95 < 10 мс (требование R1) на целевом GPU для:
      - фазы 1: узкий ROI столбика;
      - фазы 2: область захвата до 1920×1280 px, объекты 200×200 px.
    • Захват + запись не снижают FPS игры более чем на 5%.
    • GUI отзывчивость: UI-поток не блокируется инференсом (отдельные потоки).

  Отображение и DPI:
    • Корректная работа при DPI 100–200% (Per-Monitor V2).
    • Координаты ROI хранятся в логических и физических пикселях.
    • Пресеты ROI привязаны к паре (разрешение, dpi_scale).

  Надёжность:
    • При падении модели — fallback на эвристику или безопасный режим
      «только сигнал», без автоклика.
    • Автосохранение прогресса разметки каждые 30 с.

  Безопасность:
    • Данные хранятся локально; без отправки кадров в сеть по умолчанию.
    • Горячая клавиша экстренной остановки автоклика (panic key).

  Расширяемость:
    • Новая задача — без изменения ядра capture/inference, только task.yaml
      + модель + разметка.

  Логирование:
    • Структурированные логи (JSON); уровни DEBUG/INFO/WARN/ERROR.

  [ ] Разметка 100 кадров занимает ≤ 15 минут с полуавтоматической подсказкой.
  [ ] Обученная MVP-модель достигает MAE fill_ratio ≤ 0.03 на test.
  [ ] Perfect zone: Precision и Recall ≥ 0.95 на test.
  [ ] Сохранённая ONNX-модель подключается и работает после перезапуска.
  [ ] Fine-tune на 500 новых кадрах улучшает метрику на целевом поднаборе
      или откатывается автоматически при ухудшении.
  [ ] Вторая задача (другой объект) добавляется через task.yaml без правки
      ядра inference.
  [ ] ML-инференс на GPU: p95 latency < 10 мс для фазы 1 (столбик) и фазы 2
      (1920×1280, круглые объекты 200×200).
  [ ] GUI: все режимы доступны без CLI; окна сохраняют размеры после перезапуска.
  [ ] DPI 125% и 150%: ROI и захват совпадают с визуальным выделением на экране.
  [ ] benchmark_models.py выдаёт рекомендацию модели с учётом budget < 10 мс и GPU.
  [ ] GUI «Области захвата»: создание, сохранение и загрузка ROI-пресетов работает
      при DPI 125% и 150%.
  [ ] GUI «Разметка»: ручная разметка bar_bbox + fill_ratio + perfect zone;
      экспорт в data/labeled/ с train/val/test/finetune_pool.
  [ ] Универсальная модель UopilotNet: один inference даёт bbox + fill_ratio +
      perfect zone; дообучение на кругах без смены пайплайна.
  [ ] На RTX 4080: total ML latency p95 < 10 мс; в GUI отображаются замеры < 5 мс
      для фазы 1 (столбик).

13.1. Общие принципы GUI
------------------------
  • Единое главное окно (PyQt6 / PySide6) + полупрозрачный оверлей поверх игры.
  • Все окна и панели сохраняют размер/позицию при изменении (QSettings).
  • Потоки: UI-поток отделён от захвата, записи и инференса (QThread / asyncio).
  • Визуальный язык: тёмная тема, крупные кнопки, минимум кликов в горячем пути.

13.2. Вкладка «Области захвата» — сохранение зон игры
-----------------------------------------------------
  Назначение: удобно задать и сохранить прямоугольные области экрана для
  последующего сбора кадров, разметки и инференса.

  Элементы интерфейса:

  A. Список пресетов областей (левая панель)
     • Таблица: имя | задача | размер | DPI | монитор | последнее использование
     • Кнопки: «+ Новая область», «Дублировать», «Удалить», «Экспорт/Импорт»
     • Пресет хранится в presets/<name>.json:
         { name, task_id, monitor_id, roi_logical, roi_physical, dpi_scale,
           screen_resolution, hotkey, capture_fps }

  B. Интерактивное задание ROI (кнопка «Выделить на экране»)
     • Экран затемняется; пользователь рисует прямоугольник мышью.
     • Live-превью: увеличенный фрагмент с сеткой и размерами в px.
     • Привязка к задаче: fishing_bar (узкий) / game_window (1920×1280) / custom.
     • Валидация: предупреждение если ROI выходит за границы или < мин. размера.

  C. Панель «Быстрый сбор»
     • Выбор пресета ROI → «Начать запись» (горячая клавиша, напр. F9).
     • Индикатор: кадров записано, MB на диске, длительность сессии.
     • Чекбоксы: «Сохранять weak labels (ЛКМ)», «Умный сэмплинг», «Только
       при наличии столбика» (эвристика / лёгкая модель).

  D. Менеджер сессий (вкладка «Данные» или подпанель)
     • Дерево: data/raw/<session_id>/ — дата, ROI, кадров, статус разметки.
     • Действия: «Открыть в разметке», «Удалить», «Объединить сессии»,
       «Создать датасет из выбранных сессий».

  Workflow сохранения областей:
    1. Создать пресет «fishing_bar_main» → выделить ROI вокруг столбика.
    2. Создать пресет «game_field» → выделить окно 1920×1280 (фаза 2).
    3. Играть с активным пресетом → сессии пишутся в data/raw/.
    4. Сессии отображаются в менеджере; оттуда — переход к разметке.

13.3. Вкладка «Разметка» — ручной процесс аннотирования
-------------------------------------------------------
  Назначение: ручная и полуавтоматическая разметка накопленных кадров.

  Макет (трёхпанельный):

  ┌──────────────┬────────────────────────────────┬─────────────────┐
  │ Очередь      │         Превью кадра           │  Свойства       │
  │ кадров       │  (масштаб, сетка, слои)        │  аннотации      │
  │ (миниатюры)  │                                │                 │
  │              │  Слои: □ фон  □ столбик        │  fill_ratio:    │
  │ Фильтры:     │        □ заливка □ perfect     │  [====○===] 0.72│
  │ unlabeled /  │                                │  in_perfect: ☐  │
  │ low_conf /   │  Инструменты:                  │  bar_bbox:      │
  │ verified     │  [BBox] [Линия заливки]        │  [x,y,w,h]      │
  │              │  [Кисть perfect zone] [Круг]   │  Статус:        │
  │              │                                │  [verified ▼]   │
  └──────────────┴────────────────────────────────┴─────────────────┘
  │ Таймлайн: |◄ ►| кадр 45/1200  |  ■ ▶ | скорость: 1x/2x/4x          │
  └──────────────────────────────────────────────────────────────────────┘

  Инструменты разметки (ручной процесс):

  1. BBox столбика — прямоугольник; авто-ограничение ширины 8–50 px (с предупр.).
  2. Линия уровня заливки — горизонтальная линия на границе белого/прозрачного;
     fill_ratio вычисляется автоматически от bar_bbox.
  3. Кисть perfect zone — выделение зелёного градиентного сегмента вверху
     (маска или bbox; полупрозрачная зелёная подсветка поверх превью).
  4. Круг (фаза 2) — Shift+drag = идеальный круг ~200 px.
  5. Пропуск / отклонение — S = skip, X = reject (размытый/не тот кадр).

  Горячие клавиши:
    ←/→ — prev/next кадр; Ctrl+S — сохранить; P — toggle in_perfect_zone;
    1/2/3 — переключение инструментов; Space — play/pause таймлайна.

  Полуавтоматический режим:
    • Кнопка «Предразметить моделью» — заполнение всех полей от текущей модели.
    • Режим «Только правки»: показывать только кадры где confidence < порога
      или |model_fill - weak_label| > 0.1.
    • Автосохранение каждые 30 с + при смене кадра.

13.4. Сохранение размеченных данных для обучения / валидации / дообучения
---------------------------------------------------------------------------
  При нажатии «Экспорт в датасет» или автоматически по завершении пакета разметки:

  Шаг 1. Формирование версии датасета
    • Имя: dataset_<task>_<YYYYMMDD>_v<N> (напр. dataset_fishing_bar_20260606_v1).
    • Путь: data/labeled/<dataset_name>/

  Шаг 2. Структура каталога
    data/labeled/<dataset_name>/
      images/                    — PNG кадры (копии из raw, без потерь)
      masks/                     — опционально: perfect_zone, bar (PNG 8-bit)
      annotations.jsonl          — одна строка JSON на кадр (все типы R1–R5)
      splits/
        train.txt                — 70% session_id (стратификация)
        val.txt                  — 15%
        test.txt                 — 15%
        finetune_pool.txt        — кадры для дообучения (помечены finetune=true)
      dataset_manifest.json
      export_log.txt

  Шаг 3. Запись annotations.jsonl (пример)
    {
      "image": "images/frame_0045.png",
      "source_session": "uuid",
      "task_id": "fishing_bar",
      "bar_bbox": [12, 8, 32, 480],
      "fill_ratio": 0.72,
      "in_perfect_zone": false,
      "perfect_zone_bbox": [12, 8, 32, 58],
      "status": "verified",
      "split": "train",
      "finetune": false
    }

  Шаг 4. Управление сплитами в GUI
    • Вкладка «Датасеты»: список версий, статистика (кадров, verified %, split).
    • Кнопки: «Собрать train/val/test», «Добавить в finetune pool»,
      «Открыть в обучении», «Сравнить версии».
    • При дообучении: выбор base_model + finetune_pool → новая версия модели.

  Шаг 5. Инкрементальное дополнение
    • Новые размеченные кадры добавляются в finetune_pool без пересборки всего
      датасета; manifest обновляется (incremental version).
    • Опция «merge datasets» — объединение v1 + v2 с дедупликацией по frame hash.

14. ВЫСОКОСКОРОСТНОЙ ПАЙПЛАЙН: ОТ ЭКРАНА ДО МОДЕЛИ (ЦЕЛЕВОЕ ЖЕЛЕЗО)
================================================================================

14.1. Референсная конфигурация
------------------------------
  • GPU: NVIDIA GeForce RTX 4080, 16 GB GDDR6X
  • CPU: Intel Core i5-14700 (20 ядер: 6P + 8E + HT)
  • RAM: 64 GB DDR5
  • ОС: Windows 10/11, драйвер NVIDIA ≥ 535, CUDA 12.x

  Ожидаемые задержки (p95, end-to-end ML-инференс, без захвата экрана):
    • Фаза 1, ROI 128×512:   1.5–3.5 мс (TensorRT FP16)
    • Фаза 1, ROI 64×256:    1.0–2.5 мс (TensorRT FP16)
    • Фаза 2, 1920×1280:     4–8 мс (YOLOv8n TensorRT FP16, letterbox 640)
    • Бюджет R1 (< 10 мс):   выполняется с запасом 2–5× на RTX 4080

14.2. Схема пайплайна (zero-copy, минимум копий CPU↔GPU)
--------------------------------------------------------

  [Игра, GPU framebuffer]
         │
         ▼ DXGI Desktop Duplication (GPU texture, B8G8R8A8)
  [Capture Thread — CPU core E-core, приоритет Above Normal]
         │  Map GPU staging texture → numpy (неизбежная 1 копия с GPU)
         │  Crop ROI на CPU (NumPy slice, без resize) — 0.1–0.5 мс
         ▼
  [Ring Buffer — 3 слота, lock-free SPSC]
         │  uint8 [H, W, 3] в pinned host memory (cudaHostAlloc)
         ▼
  [Preprocess Thread — CPU P-core]
         │  Resize (cv2.cuda или OpenCV CPU): ROI → model input size
         │  Нормализация mean/std → float32 NCHW
         │  ~0.3–1.0 мс для 64×256; ~1–2 мс для 640×640
         ▼
  [Inference — RTX 4080, TensorRT / ONNX Runtime CUDA EP]
         │  IO binding: входной тензор уже в pinned memory → async H2D copy
         │  cudaMemcpyAsync + kernel + cudaMemcpyAsync (outputs)
         │  ~1–6 мс в зависимости от модели
         ▼
  [Postprocess — CPU P-core]
         │  Декод bbox/NMS, sigmoid fill_ratio, маска perfect zone
         │  Temporal EMA filter (3 кадра) — 0.1 мс
         ▼
  [Action Dispatcher]
         │  Решение: отпустить ЛКМ / сигнал / ничего
         └─ cooldown, panic key check

  Критично: захват экрана и инференс — в разных потоках; инференс работает
  с кадром N-1 пока захватывается кадр N (pipeline parallelism).

14.3. Оптимизации под RTX 4080
------------------------------
  1. TensorRT вместо чистого ONNX Runtime CUDA:
     • Конвертация model.onnx → model.trt (FP16, workspace 2 GB).
     • Ожидаемое ускорение 1.5–3× vs ONNX CUDA EP.
     • Сборка TRT-引擎 один раз при подключении модели (кэш на диск).

  2. FP16 inference (обязательно на 4080):
     • Потери точности MAE < +0.002 — допустимы.
     • INT8 — опционально для фазы 1, если нужен запас по latency.

  3. Pinned (page-locked) host memory:
     • Буферы захвата и preprocess в cudaHostAlloc — ускорение H2D в 2–3×.

  4. CUDA streams:
     • preprocess кадра N+1 параллельно с inference кадра N (2 streams).

  5. Batch=1, фиксированный input size:
     • Динамические размеры отключены в TensorRT — быстрее.

  6. Для фазы 2 (1920×1280):
     • Letterbox resize 1920×1280 → 640×640 (сохранение aspect ratio).
     • Альтернатива: ROI-трекинг — полный YOLO раз в 500 мс, между кадрами
       инференс только на кропе 256×256 вокруг последнего bbox (< 2 мс).

  7. Захват экрана:
     • DXGI preferred (GPU path); BitBlt — fallback.
     • Crop ROI сразу после Map, не копировать весь кадр 1920×1280 в RAM
       если ROI узкий (фаза 1).

14.4. Распределение нагрузки CPU i5-14700
-----------------------------------------
  Поток              | Ядра      | Приоритет
  -------------------|-----------|------------------
  GUI (Qt)           | E-core    | Normal
  DXGI Capture       | E-core    | Above Normal
  Preprocess         | P-core    | Above Normal
  Inference submit   | P-core    | High (короткие burst)
  Disk writer (сбор) | E-core    | Below Normal
  Training (offline) | P+E all   | Low (когда не играет)

  При 64 GB RAM: ring buffer + кэш последних 300 кадров в RAM для
  быстрого отката в разметке; запись на NVMe асинхронно.

14.5. Рекомендуемый стек для максимальной скорости
--------------------------------------------------
  • Захват: python-dxcam или собственная обёртка DXGI (быстрее mss/pyautogui).
  • Препроцессинг: OpenCV + cv2.cuda (если доступно) или NumPy + numba JIT.
  • Инференс: ONNX → TensorRT 8.6+; ONNX Runtime с TensorRT Execution Provider.
  • Очереди: multiprocessing.Queue или lock-free ring buffer (C++/pybind11).
  • Профилирование: NVIDIA Nsight Systems, встроенный latency HUD в GUI.

14.6. Мониторинг в GUI
----------------------
  • Панель «Производительность» в режиме инференса:
      capture_ms | preprocess_ms | inference_ms | postprocess_ms | total_ml_ms
      GPU util % | VRAM MB | FPS обработки | dropped frames
  • Подсветка красным если total_ml_ms ≥ 10 (нарушение R1).
  • Кнопка «Запустить бенчмарк» — 1000 прогонов, отчёт в models/benchmarks/.

14.7. Путь данных при боевом инференсе (фаза 1, кратко)
--------------------------------------------------------
  1. Пресет ROI загружен из presets/fishing_bar_main.json.
  2. DXGI захватывает только ROI ~80×500 px каждые 8–16 мс.
  3. Preprocess → 64×256 float16 NCHW в pinned buffer.
  4. TensorRT UopilotNet → bar_bbox, fill_ratio, perfect_zone_score.
  5. EMA + правило: if in_perfect_zone and fill rising → release LMB.
  6. Общий ML latency p95 на RTX 4080: ~2–4 мс (запас до лимита 10 мс).
